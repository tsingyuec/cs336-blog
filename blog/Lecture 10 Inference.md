# Lecture 10: Inference

## 本讲要解决的核心问题（SCQA）

**背景（Situation）**：前几讲我们都在讲"怎么把模型训出来"。这一讲换个方向，讲**推理（inference）**：你已经有一个训练好的模型，输入一个 prompt，希望它尽可能准确、快速地吐出回复。这件事看似简单，但它是语言模型真正被用起来的那一步——聊天助手、代码补全、agent、批量数据处理、甚至强化学习里的 rollout 生成，全都建立在推理之上。([【跳转到 00:00】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=0)、[【跳转到 00:42】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=42))

**冲突（Complication）**：训练和推理在硬件上的行为**根本不同**。训练时，你能一次性看到整个序列的所有 token，可以在**序列维度上并行**——注意力、MLP 都变成一次"大张量相乘"，硬件能被喂饱，算术强度高、效率好。但推理是**自回归**的：token 必须一个一个按顺序生成，你没法在序列维度并行。于是推理变成了一堆又薄又碎的矩阵运算，硬件大部分时间在等着搬数据，而不是在算数。更麻烦的是，在 agent 时代，模型生成的绝大多数 token 根本不是给人读的，而是"思考、推理、调用工具、自我检查"的中间过程——token 数可以无限增长，推理花的算力几乎没有上限。([【跳转到 01:57】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=117)、[【跳转到 05:38】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=338))

**疑问（Question）**：推理到底慢在哪里？它的根本瓶颈是什么？有哪些技术能在**不掉太多精度**的前提下，让推理显著变快——无论是延迟、吞吐量还是首 token 时间？

**回答（中心思想，结论先行）**：推理的核心结论只有一句话——**预填充（prefill）阶段是计算受限（compute-bound），生成（generation）阶段是内存受限（memory-bound）**。瓶颈的根源是：生成阶段每个 token 只做一次极薄的矩阵乘法，注意力的算术强度约为 `1`，而 H100 这类加速器的算术强度高达约 `295`，两者差了两个数量级，GPU 的算力被白白浪费在等待内存搬运上。

于是一切优化都围绕同一条原则展开：**减少内存搬运，尤其是缩小 KV 缓存（KV cache），同时尽量不损害精度。** 具体手段可以归成四类：

1. **缩小 KV 缓存**：分组查询注意力（GQA）、多头潜在注意力（MLA）、跨层注意力、滑动窗口/局部注意力、线性注意力，以及 DeepSeek 的压缩/稀疏注意力；
2. **从系统与模型层面把模型变小**：量化（QAT/PTQ/GPTQ/激活感知量化）与剪枝；
3. **无损加速**：推测解码（speculative decoding），用"检查比生成快"的不对称性一次接受多个 token；
4. **应对动态负载的系统技巧**：连续批处理（continuous batching）与分页注意力（PagedAttention）。

同时要记住一个贯穿全讲的取舍：**延迟与吞吐量经常相互制约**（增大 batch 提升吞吐却恶化延迟），但只要能降低内存占用，两者有时又能同时改善。本讲最后会点出一个开放方向：Transformer 的注意力/KV 结构天生对推理不友好，状态空间模型、线性注意力、扩散模型等"为推理而生"的新架构仍有巨大潜力。([【跳转到 66:34】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3994))

> 本讲大量参考了 Google 出的那本关于 Transformer 与推理的 *scaling book*，讲者也直接借用其中若干图，值得配套阅读。([【跳转到 07:01】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=421))

## 一、推理是这个时代最值得优化的账：它反复发生，而且几乎没有上限

要理解为什么这门课要专门花一讲讲推理，先得想清楚它的"经济账"。结论是：**训练是一次性的大成本，做完就结束了；推理却是每天都得反复支付的账单，而且随着 agent 兴起，这张账单几乎没有上限。** 下面分三点展开。

### 1.1 训练一次性、推理天天付

讲者把这件事讲得很直白：训练这类模型的成本可能非常高、确实非常高，但它**做完也就完了**；而推理是**反复产生的成本**，"你基本每天都得为它买单"。([【跳转到 01:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=67))

[【跳转到 00:00】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=0) 的幻灯片整理得非常清楚：推理出现在很多地方——**实际使用**（chatbot、代码补全、agent、批量数据处理）、**模型评估**（比如写指令跟随这类需要生成才能评的任务）、**强化学习**（先大量采样生成 rollouts，再给它们打分，然后更新权重）。而为什么"效率"重要？因为训练是一次性成本，推理是重复很多次的那一方。([【跳转到 00:00】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=0))

![推理的"经济账"：训练是一次性成本，推理是反复发生的成本；幻灯片估计 OpenAI 每天处理约 8.6 万亿 token，作为对比一个前沿开源模型预训练约 32 万亿 token。](assets/p10/00092.jpg)

一个很有冲击力的数字对比：据估计，**OpenAI 每天产生约 8.6 万亿（8.6×10¹²）个 token**；而作为参考，一个前沿开源模型（讲者提到 DeepSeek V4）的预训练数据量约 **32 万亿** token。换句话说，**不到四天时间，光推理生成的 token 数量和对应算力，就至少相当于训练一个前沿模型。** 即便前沿模型的训练用 token 可能更多，推理端的累计量仍然会更高。([【跳转到 01:32】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=92))

### 1.2 agent 让 token 不再只给人读

过去一年，推理的重要性明显上升，原因在于**用途变了**。以前我们觉得语言模型主要是个 chatbot 或助手：人输入一个 prompt，模型返回一段回复，而**人类的目标就是读这段回复**。人的阅读速度就那样，所以一旦生成速度超过阅读速度，再快也没多大用。([【跳转到 01:57】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=117))

但进入 **agentic（智能体化）** 世界后，情况完全不同：你发起一个查询，agent 会去做一堆事——它会思考、推理、调用工具、自我检查，最后才把结果整理出来给人看。也就是说，**agent 生成的大部分 token 其实都不是给人读的**。既然如此，你就应该把"生成的 token 数"直接看成"花掉的算力"，而这**本质上没有上限**：问题越大，需要的算力和 token 就越多。对 chat 类推理来说，快到某个点就够了（受限于人的阅读速度）；但对 agent 来说，从推理里多压榨出一点性能，带来的价值是没有上限的。([【跳转到 02:22】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=142)、[【跳转到 02:47】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=167))

### 1.3 谁在做推理：闭源服务商与开源推理栈

推理既然这么重要，商业上自然有大量玩家。可以分成两类：

- **闭源 API 提供商**：所有提供服务、售卖模型的厂商（如 OpenAI、Anthropic、Google 等）都必须为自己模型的推理负责，这对他们是件大事。
- **开源权重模型的服务商**：专门服务开源权重模型、也提供推理服务。

如果自己动手搭推理服务，有几个流行的开源软件包值得记住（[【跳转到 03:12】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=192)、[【跳转到 03:33】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=213)）：

| 软件包 | 特点 |
| --- | --- |
| **vLLM** | 出自伯克利，首创 PagedAttention，目前最流行、可作默认选择 |
| **SGLang** | 同样出自伯克利，首创 RadixAttention，在 agentic 工作负载上表现特别好 |
| **TensorRT-LLM** | NVIDIA 出品，对 GPU 高度优化、速度极快，但适用范围相对窄 |
| **llama.cpp** | 纯 C++，支持 CPU 推理、可本地运行 |

一句话总结：**推理是件大事，让它变快非常重要**——如果你能让推理快一倍、哪怕只快 10%，那都是件大事。([【跳转到 03:33】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=213))

## 二、衡量"快"要看三个不同指标：TTFT、延迟与吞吐量

既然目标是"快"，下一个问题就是：**到底什么是"快"？** 讲者指出，"快"并没有唯一指标，而是有几个适用于不同场景、彼此各有取舍的指标。结论先说：**TTFT 管"开始生成前的等待"，延迟管"单个用户看到 token 的速度"，吞吐量管"服务多个查询时的总体速度"。**([【跳转到 03:58】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=238))

![三个"快"的指标：首 token 时间（TTFT，开始生成前用户要等多久）、延迟（单个查询每秒/每 token 的出词速度）、吞吐量（面向多查询时每秒能处理多少 token）。](assets/p10/00238.jpg)

### 2.1 首 token 时间（TTFT）

**首 token 时间（Time To First Token，TTFT）**，指的是**用户在开始看到任何生成内容之前要等待的时长**。比如你把查询发给 ChatGPT，从发出到"第一个 token 冒出来"的那一刻，就是 TTFT。它对交互式应用特别有用，因为那种"干等着、什么也做不了"的延迟越长，用户体验就越差。([【跳转到 03:58】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=238))

### 2.2 延迟：单个查询的出词速度

**延迟（latency）** 是从**单个用户**的角度看，一次查询里 token 冒出来的速度有多快（常以"秒/ token"计量）。等第一个 token 出来之后，速度未必需要那么快——反正人要读，也读不了那么快。但它对交互式应用仍然重要，基本上就是**流式输出的速度**。([【跳转到 04:23】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=263))

### 2.3 吞吐量：多查询下的总速度

**吞吐量（throughput）** 是**面向多个查询时，每秒总共能处理多少个 token**（常以"token / 秒"计量）。延迟（或它的倒数）和吞吐量关系密切，往往很一致。如果你做的是**大量批量处理**——比如有一批 KB 级的数据想用语言模型处理掉——吞吐量就很有用：你只想把这活干完，单个查询快是慢、先来后到都无所谓。([【跳转到 04:48】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=288)、[【跳转到 05:13】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=313))

### 2.4 三个指标的取舍

总体来看，很多优化手段能**同时**改善延迟和吞吐量，但后面会看到这里存在**权衡**。最典型的就是那对矛盾：**小 batch 延迟低但吞吐差，大 batch 吞吐高但延迟差。** "快"到底指哪一面，取决于你的应用更看重什么。([【跳转到 04:48】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=288))

## 三、用 einops 式的记号给 Transformer 建模

要精确讨论"慢在哪"，先得有一套能描述张量形状和计算量的语言。讲者的做法是：**借用 einops 的风格，用字母表示维度及其长度，再用颜色标注每个维度在运算中的角色。** 这套记号是理解后面所有推导的基础。([【跳转到 07:26】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=446))

### 3.1 维度的三种角色：收缩、常规、批处理

最核心的约定是三种维度角色（[【跳转到 07:51】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=471)）：

- **收缩维度（红色，contracting）**：**同时出现在两个操作数里，却从结果中消失**。比如 `BTD × DH → BTH` 里的 `D`，它是被"内积掉"的那一维。
- **常规维度（黑色，regular）**：**只在一个操作数里出现，并保留到结果中**。比如 `B`、`T`、`H`。
- **批处理维度（蓝色，batching）**：**既出现在两个操作数里、也保留在结果中**，它不会被收缩或缩减。比如 `BD × BD → B` 里的那个 `B`（这里其实是把 `D` 逐元素相乘后收缩）。

为什么要区分这三种角色？因为它直接对应到"计算有多密集"。红色维度被收缩，意味着**它上面的元素要被两两相乘后求和**——这正是矩阵乘法产生大量浮点运算（FLOPs）的来源；而批处理维度只是"平行地多做几份"，不会额外增加单个结果的运算量。

幻灯片会把这一套讲得比文字更直观：`BTD × DH → BTH` 说明一个序列、每个 token 位置的向量都乘以同一个矩阵；`BD × BD → B` 则说明在批处理维度 `B` 上逐份做点积。([【跳转到 07:26】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=446))

### 3.2 Transformer 模块的张量与形状

用这套记号，讲者给出了一个"电路图"式的 Transformer 模块描述——他特别强调，这可能是对"Transformer 到底是什么"最清晰的定义之一，因为它明确告诉你**每个张量的确切形状**，从而能理清它们之间的依赖关系。([【跳转到 08:41】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=521))

![Transformer 模块的"电路图"：左侧是注意力计算流（Q/K/V 投影、reshaping、mask、softmax），右侧是符号与维度、以及全讲的强度公式；这张图把张量形状和依赖关系标得最清楚。](assets/p10/01582.jpg)

流程是：取某一层的激活值 `X`，先输入注意力机制，再输入 MLP。注意力里，`X` 分别用查询、键、值矩阵投影出来（[【跳转到 09:06】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=546)）：

- `B` = batch 维度，也就是序列的数量；
- `T` / `S` = 序列维度，也就是 token 的数量；
- `D` = 模型维度（`d_model`，嵌入维度）；
- `F` = MLP 隐藏维度，按惯例约为 `4D`；
- `H` = 每个注意力头的维度，`N` = 查询头数量。

注意力里 `B` 会**在两处都出现**（Q 和 K/V 都带 `B`），而 `head` 维度被收缩。讲者请大家先记住这个"蓝色 `B`"——后面讲"为什么推理难做、注意力为什么是瓶颈"时会反复用到它。MLP 则简单直接：门控 + 上投影 + 下投影几次矩阵乘法，本质上就是一次大矩阵乘法。([【跳转到 09:31】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=571)、[【跳转到 09:56】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=596))

### 3.3 GQA 的 K/G 记号与 S/T 的区别

有两个记号上的细节，初学者最容易搞混：

1. **分组查询注意力（GQA）的拆分**：`head` 的总数会被拆成"**组数 `K`**"与"**每组里的 head 数 `G`**"。不过讲者在课堂上被同学纠正过一次：他一开始把 `K` 和 `G` 的含义说反了，后来确认——**`K` 代表（KV）组的数量，`G` 代表每个组里的 head 数**（即 `N = K × G`）。这里顺便记住：普通多头注意力 `K = N`（不缩减），多查询注意力 `K = 1`（效果太差、基本没人用），GQA 在两者之间取平衡。([【跳转到 09:31】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=571)、[【跳转到 15:37】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=937))
2. **`S` 与 `T` 的区别**：两者都表示序列维度，但 **`S` 是输入 token 的数量（作为条件的部分），`T` 是输出 token 的数量（要生成的部分）**。训练阶段 `T = S`（模型把所有输入当作输出来预测）；推理阶段，预填充时 `T = S`，生成时 `T = 1`。这个 `S/T` 的区分是本讲后面所有公式的关键。([【跳转到 10:46】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=646))

## 四、算术强度是判断"计算受限还是内存受限"的标尺

接下来进入本讲的数学核心。要回答"推理慢在哪"，需要一把标尺来量一件事——**一个运算到底是"算得不够忙"还是"搬得不够快"**。这把尺子就是**算术强度（arithmetic intensity）**。结论先行：**算术强度 = 浮点运算量 ÷ 传输字节数，即"每搬运一个字节做了多少计算"。它越大越好；把它和硬件的算术强度一比，就知道你是计算受限还是内存受限。**([【跳转到 11:11】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=671))

### 4.1 算术强度是什么

算术强度的定义是：

```text
intensity = FLOPs / bytes_transferred
```

其中 FLOPs 是浮点运算次数，bytes_transferred 是从高带宽内存（HBM）搬到计算单元（SRAM）的字节数。**强度越高，说明每搬一个字节干了越多计算，越能掩盖内存访问的开销。**([【跳转到 12:26】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=746))

### 4.2 矩阵乘法的 FLOPs 与字节数推导

用热身练习来建立直觉：做一个 `B×D` 的矩阵 `X` 与 `D×F` 的权重 `W` 的乘法，用 bf16 存储（推理时通常如此），数据量就是每项 2 字节。逐步记账如下（[【跳转到 11:36】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=696)、[【跳转到 12:01】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=721)）：

```text
从 HBM 读 X (B×D):   2*B*D 字节
读权重 W (D×F):      2*D*F 字节
矩阵乘法:            2*B*D*F FLOPs
写回结果 (B×F):      2*B*F 字节
```

![矩阵乘法的算术强度记账：读 X、读权重、做 2*B*D*F 次浮点运算、写回结果；关键观察是"读写量近似二次、计算量是三次"，只有这样才能实现高算术强度。](assets/p10/00721.jpg)

这里有个非常重要的规律：**读写的数据量大概是个"二次"的量（比如 `B*D`、`D*F`），而矩阵乘法的浮点运算量是"三次"的（`B*D*F`）。** 讲者强调，记住这一点很关键，因为**只有这样你才能实现高算术强度**——当维度变大时，计算量的增长速度超过搬数据的速度，强度就上去了。([【跳转到 12:01】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=721))

于是总的 FLOPs 就是那个三次项，而传输字节数是读写之和。做一个简化假设：**batch 维度远小于 `D` 和 `F`**（令 `D = c·B`、`F = c·B`，并让 `c → ∞`），那么强度就化简为：

```text
intensity == B
```

也就是说，**这个矩阵乘法的算术强度约等于 batch 大小 `B`**。([【跳转到 12:51】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=771))

### 4.3 与硬件算术强度比较：H100 的约 295

有了"运算的强度"，还要有"硬件的强度"来对照。**硬件的算术强度 = 每秒浮点运算数（FLOPs）÷ 内存带宽**——也就是硬件每从 HBM 读一个字节，能配得上多少计算能力。把两者比一比（[【跳转到 13:16】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=796)、[【跳转到 13:41】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=821)）：

- 如果你的**运算强度 > 硬件强度**：说明你受限于**计算能力**，是**计算瓶颈**，这是**好事**（计算单元被喂饱了）；
- 如果**运算强度 < 硬件强度**：说明你受限于**内存带宽**，是**内存瓶颈**，硬件在空转等数据。

以 **H100** 为例，规格大约是 `989e12` FLOPs/秒、内存带宽 `3.35e12` 字节/秒，于是硬件的算术强度约为：

```text
accelerator_intensity = 989e12 / 3.35e12 ≈ 295
```

也就是说，前面那个矩阵乘法要进入"计算受限"的好状态，batch 大小大概得超过 **295**。

### 4.4 batch=1 的极端情况

反过来看极端情况就更能明白推理的处境：假设你**只有一个样本（B=1）**，那么算术强度大约是 `1`，**远远低于 295，此时严重受限于内存带宽**。你读取了整个 `D×F` 的权重矩阵，却只做了 `2×D×F` 次浮点运算——**读权重的开销被一个样本"独吞"了**。([【跳转到 14:06】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=846))

这正是推理阶段会遇到的工作负载：**你拿到的不是完整的、粗壮的大矩阵，而是这种非常薄的矩阵或张量。** 记住这个画面，下一节我们会看到它如何演变成生成阶段的根本瓶颈。

## 五、KV 缓存把推理拆成"预填充"和"生成"两阶段

前面建立了算术强度的标尺，现在把它用到真实的推理流程上。这一节的结论是：**朴素地逐 token 重新计算整段序列代价高达 `O(T³)`；利用因果注意力"前缀不变"的性质，可以用 KV 缓存把推理拆成"预填充"（可并行）和"生成"（逐 token）两个阶段，从而省掉大部分重复计算。**([【跳转到 15:57】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=957))

### 5.1 朴素做法为何是 O(T³)

最朴素的做法是这样的：把 prompt 输入 Transformer，生成 keys、values 和激活值，最后在输出词表上得到 logits，采样出一个 token；把这个 token 拼到 prompt 后面，再重复一遍，以此类推。如果把它看成一个黑盒，输入序列就输出 token 分布，反复套用确实"行得通"，但效果真的很差。([【跳转到 15:57】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=957)、[【跳转到 16:22】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=982))

![朴素推理的问题：每生成一个 token 都要把整段历史重新喂进 Transformer，生成 T 个 token 的复杂度是 O(T³)（注意力单次是 O(T²)，且每个 token 都重算一遍）。](assets/p10/01082.jpg)

代价分析：每生成一个 token，你要花 `O(T)` 量级的时间（`T` 是此刻已生成的 token 总数）；注意力本身的计算量是 `T` 的平方（这部分绕不开），并且**每个 token 都要从头算一遍**，所以**生成 `T` 个 token 的复杂度其实是 `T` 的三次方**。这效率相当低。([【跳转到 16:47】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1007))

### 5.2 因果注意力允许跨前缀复用

但讲者指出，**很多计算其实可以跨前缀复用**。打个比方：生成 "never gonna give you up" 时，前面那些 token 的键和值其实是不变的——因为我们是**因果（decoder-only）Transformer**。如果是双向模型，你追加一个新 token 会让前面所有状态都变；但因果模型里，你往后追加 token 时，**前面这些激活值（activations）不会变**。([【跳转到 17:12】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1032))

基于这个观察，最显而易见的做法就是**在 HBM 里存一个 KV 缓存（KV cache）**，这样在连续生成 token 之间，就能直接复用之前算好的键和值，而不必重算。([【跳转到 17:37】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1057))

### 5.3 KV 缓存的形式与两阶段

KV 缓存在形式上是：**对每个序列（共 `B` 个）、对每个 token（共 `S` 个）、对每一层、在每个 head 中，存储一个 `H` 维的向量**（键一份、值一份）。([【跳转到 18:52】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1132))

![KV 缓存与推理两阶段：定义"每个序列/每个 token/每层/每个 head 存一个 H 维向量"；预填充（prefill）把 prompt 编码成向量、可像训练一样并行；生成（generation）逐个出 token；之后分别对 MLP 层和注意力层算 FLOPs 与内存 IO。](assets/p10/01207.jpg)

有了 KV 缓存，推理就分成两个性质迥异的阶段：

1. **预填充（prefill）**：拿到完整 prompt，把它编码成关键/值向量，**填满 KV 缓存**。因为你能看到完整的 prompt，所以这一步**和训练一样可以并行**（此时 `T = S`）。
2. **生成（generation）**：按顺序逐个生成新的回复 token。对已经看过的 token，你**不用再花开销重新计算它们的 KV 缓存**，只需为新 token 计算（此时 `T = 1`）。

([【跳转到 19:17】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1157))

这个拆分是后面所有优化的舞台：**预填充能并行、天生高效；生成只能串行、天生低效。** 接下来就分别对 MLP 层和注意力层做 FLOPs / 内存分析，看看这两个阶段各自受什么限制。

## 六、逐层分析得出核心结论：预填充计算受限、生成内存受限

这一节是全讲的"高潮"。结论先行：**把 MLP 层和注意力层分别做算术强度分析后会发现，MLP 不是问题（只要 batch 够大），真正的瓶颈是生成阶段的注意力——它的算术强度仅约 `1`，且完全不随 `B` 缩放。这就是"推理是内存受限的"这句话的来历。**([【跳转到 26:47】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1607))

只看矩阵乘法就够了，因为真正费计算量的就是它们，其余部分浮点运算量不大、可以并进矩阵乘法里。([【跳转到 20:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1207))

### 6.1 MLP：强度约 B×T，本质是一次大矩阵乘法

先算 MLP：从内存读 `X`、读权重，计算上投影并写入 HBM，再算门控、下投影，写回 HBM。FLOPs 取决于 `B`、`T`、`D`、`F`（批量大小、序列长度、模型维度、前馈维度），传输字节数是相应的读写之和。算出强度后，仍然做"`B×T` 远小于 `D`、`F`"的简化，得到（[【跳转到 20:32】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1232)、[【跳转到 20:57】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1257))：

```text
MLP intensity ≈ B*T
```

这和单纯矩阵乘法的情况很像——**MLP 本质上就是一次大矩阵乘法**，而且批处理维度和序列长度维度基本互不影响、各自独立。([【跳转到 21:22】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1282))

- **预填充阶段**：`T = S` 很大，只要把 `B×T` 设得足够大（大批量、长序列），MLP 就能保持高算术强度，**没问题**。
- **生成阶段**：`T = 1`，于是强度约等于 `B`。此时 `B` 是并发请求数（或并发用户数），可能高也可能低、还随时间变化。不过总体还好——**只要 batch 够大**，强度就不会太差；这里序列长度帮不上忙，但 batch 能帮上忙。

### 6.2 注意力：生成阶段强度约 1，且不随 B 缩放

注意力就不一样了。它要从 HBM 读取 Q、K、V，计算注意力、softmax，算出值矩阵再写回 HBM。它的 FLOPs 是 `B×S×T×D`，传输字节数是相应的读写之和。所有项都是矩阵乘法，所以**浮点运算量的阶数总比传输字节数高一阶**，关键在于"系数"长什么样。注意力这个系数是 `1/(1/S + 1/T)`，也就是（[【跳转到 22:37】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1357)、[【跳转到 23:02】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1382)、[【跳转到 23:27】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1407)、[【跳转到 23:52】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1432))：

```text
attention intensity = S*T / (S + T)
```

两个阶段代进去：

- **预填充**（`T = S`）：`intensity = S/2`。这**很好**——只要序列够长，注意力也能维持高算术强度。
- **生成**（`T = 1`）：`intensity = S/(S+1)`，也就是**接近 1**。而"强度只有 1"是很糟糕的：我们希望它达到约 `295`，才能让 H100 跑满。**这就是瓶颈所在。**

![注意力的算术强度：统一公式为 S*T/(S+T)；预填充时 T=S 得 S/2（不错），生成时 T=1 得 S/(S+1)≈1（很差）；与 MLP 不同，它没有 B 依赖，所以增大 batch 对注意力帮助有限。](assets/p10/01432.jpg)

### 6.3 为什么注意力是根本瓶颈

为什么 MLP 生成没问题、注意力却卡住了？关键在于**是否依赖 `B`**（[【跳转到 24:42】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1482)、[【跳转到 25:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1507)、[【跳转到 25:32】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1532))：

- **MLP 里，每个序列都用同一组 MLP 权重**，这些权重**不依赖 `B`**。所以你只要把权重加载一次，就能用它处理整批数据——**批量越大越有帮助**，因为权重的读取开销被更多序列分摊了。这就是 MLP 能达到高算术强度的原因。
- **注意力里，每个序列都有自己的 KV 缓存**，Q/K/V 全都**依赖 `B`**。每个序列其实是各自做一次独立的（点积式）运算，它们彼此独立，所以"多做几次矩阵乘法"并不能分摊什么成本。这个不随 `B` 缩放的"蓝色 `B`"，正是**算术强度无法随 batch 提高的原因**，也正是瓶颈所在。

讲者打了个很贴切的比方：注意力里本质是在做一批**点积**，而点积的算术强度糟糕透了——读一堆数据只做很少的计算，几乎纯粹在搬内存。([【跳转到 25:57】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1557))

### 6.4 结论

把两阶段、两层的结果汇总（[【跳转到 26:22】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1582)、[【跳转到 26:47】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1607))：

| 阶段 | MLP 强度 | 注意力强度 | 受限类型 |
| --- | --- | --- | --- |
| 预填充（prefill） | `B×S`（好） | `S/2`（不错） | **计算受限** |
| 生成（generation） | `≈B`（batch 大就行） | `S/(S+1)≈1`（极差） | **内存受限** |

于是得到本讲最该记住的一句话：

> **预填充阶段是计算受限的，生成阶段是内存受限的；真正棘手的根本瓶颈，是生成阶段那极低的注意力算术强度。只要你还用 Transformer，这个问题就无法真正消除。**

所以每当你听到别人说"inference 是内存受限的"，现在你应该明白**为什么**了：因为生成阶段的时间几乎全花在把 KV 缓存和权重从 HBM 搬来搬去，而不是花在计算上。这一认识的好处是"简化"——考虑耗时的时候，只要看需要搬运多少内存就行。([【跳转到 27:12】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1632))

## 七、实例：Llama 2 13B 在 H100 上的延迟与吞吐权衡

概念讲完，讲者用一个具体例子把数字落到实处：**Llama 2 13B 跑在 H100 上，延迟和吞吐量各是多少？** 结论先行：**延迟随 batch 线性增长（常数项就是 KV 缓存），吞吐量随 batch 增长但有上限；这就形成了"要延迟还是要吞吐"的两难。**([【跳转到 27:37】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1657))

### 7.1 配置与参数量核算

用到的模型配置如下（[【跳转到 28:02】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1682)）：

| 符号 | 含义 | 数值 |
| --- | --- | --- |
| `S` | 序列长度 | 1024 |
| `D` | 模型维度 | 5120 |
| `F` | 前馈维度 | 13824 |
| `N` | 查询头数 | 40 |
| `K` | KV 头数 | 40（即 `K = N`，未做 GQA 缩减） |
| `H` | 头维度 | 128 |
| `L` | 层数 | 40 |
| `V` | 词表大小 | 32000 |
| — | H100 内存带宽 | `3.35e12` 字节/秒 |

参数量按**嵌入层 + MLP 层 + QKV 投影**相加，用 bf16 存储。算出来是 `13,015,449,600`，也就是约 **130 亿**——这正好和"13B"的名字对得上，是个很好的合理性检验。([【跳转到 30:32】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1832))

KV 缓存的大小则是：

```text
KV_cache = S × N × K × H × L × 2(key/value) × 2(bf16 字节)
```

总内存占用是"单个序列的 KV 缓存 × B + 参数大小"。([【跳转到 29:17】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1757))

### 7.2 内存、延迟、吞吐的公式

因为推理内存受限，**延迟主要由内存 IO 决定**——数据要在 HBM 和 SRAM 之间来回传输，"移动数据所花的时间"就是延迟的主要部分（前提是通信和计算能重叠）。而吞吐量是延迟的倒数；因为要并行生成 `B` 个 token，数值上还会多出一个 `B` 的因子。代入配置后得到（[【跳转到 29:42】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1782)、[【跳转到 30:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1807)）：

```text
memory     = 838860800*B + 26030899200        (字节)
latency    = 0.00025046*B + 0.0077704         (秒/token)
throughput = 127792.358*B / (32*B + 993)      (token/秒)
```

### 7.3 数值结果与 batch 的两难

几个关键读数（[【跳转到 31:47】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1907)、[【跳转到 32:12】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=1932)、[【跳转到 33:22】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2002)、[【跳转到 33:47】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2027))：

- **延迟是 `B` 的线性函数**，常数项就是参数搬运、随 `B` 增长的项就是 KV 缓存——因为处理时要把越来越大的 KV 缓存反复复制。
- **吞吐量约等于 `B/(B + 常数)`**：随 `B` 增大而提高，但**存在渐近上限**，不可能无限增长。而且它往往**先撞上 H100 的显存上限**（KV 缓存把显存吃光），即便换成 B200 把 batch 调得更大，最终也还是会撞墙。
- 当 **batch = 1** 时：延迟约 **0.008 秒/token**、吞吐约 **124 token/秒**。
- 当 **batch 增大**时：延迟变**差**、吞吐变**好**。

这就形成了本讲反复强调的取舍：**小 batch 延迟低但吞吐差，大 batch 吞吐高但延迟差。** "快"到底指哪一面，取决于你的应用。讲者用了个"公交"的比喻：公交一次能载很多人、吞吐高，但你得等大家都上车；增大 batch 提升吞吐，靠的是**参数共享**——模型只需加载一次就能处理很多序列；代价是批处理要"等大家都跑完"，所以延迟高。([【跳转到 34:12】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2052))

### 7.4 并行化与 TTFT

还有两个补充点（[【跳转到 34:37】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2077)、[【跳转到 35:02】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2102))：

1. **并行化**：可以把模型切分、放到多个设备上跑。一个简单例子是启动 `M` 个模型副本：**延迟不变，但吞吐量能提升到 `M` 倍。** 更深入的并行策略可参考 scaling book 的推理章节。
2. **TTFT**：首 token 时间基本就是**做 prefill 所花的时间**，因为 prefill 一结束你就能开始生成。想要**更快的 TTFT，就要用较小的 batch**；想要**更高的吞吐，就要用较大的 batch**——又是一个同一枚硬币的两面。

## 八、缩小 KV 缓存：GQA、MLA 与更多共享/压缩思路

既然**内存是推理的瓶颈、KV 缓存又特别占内存**（batch 足够大时，KV 缓存甚至可能超过参数本身的规模），优化方向就很明确了：**在尽量不损失精度的前提下，把 KV 缓存降下来。** 这一节从"在 head 之间共享 KV"讲到"把 KV 压缩成潜变量"，再到"减少/跳过部分 KV"。([【跳转到 35:52】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2152))

### 8.1 GQA：在 head 之间共享 KV

**分组查询注意力（Grouped-Query Attention，GQA）** 的思路是：**查询（queries）的数量不变，但只保留一部分键/值组**，每个组内的多个查询头共享一份键和值。用前面 `K`/`N` 的记号说：**GQA 把键/值的数量从 `N` 个减到 `K` 个，于是 KV 缓存缩小到原来的 `K/N`。**([【跳转到 36:17】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2177)、[【跳转到 37:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2227))

![GQA 对比图：多头注意力（MHA）每个查询头都有独立的 K/V；多查询注意力（MQA）让所有查询头共享同一份 K/V（K=1）；GQA 取两者之间，每个"组"的查询头共享一份 K/V。](assets/p10/02227.jpg)

这是三种方案的光谱：

- **MHA（多头注意力）**：`K = N`，不缩减，KV 缓存最大；
- **MQA（多查询注意力）**：`K = 1`，所有查询头共用一份键/值，压缩最狠，但**效果太差，基本没人用**；
- **GQA**：介于两者之间，**希望在精度和速度之间找到平衡点**。

GQA 原论文（Ainslie 等，2023）的实验给出很直观的结论：全注意力（MHA）耗时非常高；从 `K=1` 起步速度飞快；把 `K` 加到 8 效果还不错；再往上收益就**到顶**，耗时反而明显上升。所以工程上要选一个合适的组数，而不是一味求小。([【跳转到 37:12】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2232))

**为什么 GQA 能同时降低延迟、提升吞吐？** 因为它把 KV 缓存缩到了 `K/N`，而省内存就能提速——我们的系统本来就是内存瓶颈。用数字说话：还是刚才那个 Llama 例子、用 batch=64，假定一个压缩比例，KV 内存降下来后**延迟改善、吞吐量也上去了**；而且还能顺手把 batch 调得更大（比如原来 batch=256 会爆显存，现在装得下了），吞吐进一步成比例上升。这说明一个很重要的点：**延迟和吞吐量并不总是冲突的，只要把内存占用降下来，两者都能变好；真正的矛盾点其实在 batch 这个维度上。**([【跳转到 38:02】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2282)、[【跳转到 38:27】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2307)、[【跳转到 39:17】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2357))

当然，**任何有损改动都要检查准确性**。GQA 论文报告的效果普遍不错，但讲者提醒要"打个折扣"看——毕竟只是针对特定模型的结果；后来的 DeepSeek 论文表明，压缩 KV 确实会带来一定负面影响。**除了纯数学部分，其他结论都值得保持一点怀疑。**([【跳转到 39:42】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2382)、[【跳转到 40:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2407))

### 8.2 MLA：把 KV 压缩到潜变量

**多头潜在注意力（Multi-head Latent Attention，MLA）** 是 DeepSeek 提出的更激进的思路。它和 GQA 的区别在于：**GQA 减少键/值的"数量"（head 数），MLA 则保持每个 token 一个键/值，但把它们"参数化压缩"起来。**([【跳转到 40:24】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2424))

![MLA 对比图：MHA/GQA/MQA 都直接缓存 K/V；MLA 则先把激活投影压缩成一个小的潜变量 C（只在推理时缓存它），需要时再还原出 K、V，从而大幅压缩 KV 缓存。DeepSeek V2 把 N*H=16384 压到 C=512。](assets/p10/02474.jpg)

具体做法（[【跳转到 40:49】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2449)、[【跳转到 41:14】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2474)）：

- 常规做法是：拿到激活值，乘一个矩阵得到 `K`、乘另一个矩阵得到 `V`，维度通常是 `N×H`，跟模型维度差不多大；
- MLA 则把激活值投影、**压缩到一个较小的 `C` 维潜变量**，然后只缓存这个 `C`（小得多）；等需要键和值时，再从 `C` 还原出 `K` 和 `V`。DeepSeek V2 把维度从很大的 `N*H = 16384` 直接压到 `C = 512`，压缩相当激进。

有一个技术细节：**MLA 与 RoPE（旋转位置编码）的兼容性**。因为 RoPE 是直接作用在键/值上的，而 MLA 压缩后再还原会破坏这个作用，所以他们的做法是**额外增加一些维度来处理 RoPE**（这也解释了为什么实际维度是 `512 + 64 = 576`）。总的来说缩减幅度仍然很大，所以延迟和吞吐量都能明显改善——道理很简单：**KV 缓存越小，跑起来就越快**（在某个点之前基本是线性扩展）。([【跳转到 41:39】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2499)、[【跳转到 41:44】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2504))

有意思的是，DeepSeek 论文的结果**与 GQA 论文有点张力**：他们报告 MLA 甚至比 MHA 还略好一点，而 GQA 则相对差一些。讲者的态度很谨慎——除非你亲自做消融，否则很难预判哪种压缩方式最适合你的模型，**"得靠大量实验，看看哪种方法管用"。**([【跳转到 42:27】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2547)、[【跳转到 42:50】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2570))

### 8.3 跨层注意力、滑动窗口与线性注意力

除了在 head 维和模型维上做文章，还可以在**层（layer）**和**序列长度**上做文章：

- **跨层注意力（cross-layer attention）**：GQA 是在 head 之间共享 KV，跨层注意力则在 **layer 之间共享**——只计算其中一部分层的 KV，其余层**直接复用上一层的 KV 缓存**。实验显示它能优化帕累托前沿（Pareto frontier），即在这些模型上每个点都更好。([【跳转到 43:15】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2595)、[【跳转到 43:40】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2620))
- **局部/滑动窗口注意力（sliding-window / local attention）**：完整注意力矩阵是 `N` 的平方，而滑动窗口的想法很自然——**生成每个 token 时只看最近的 `K` 个 token**。这样一来，**KV 缓存就和序列长度无关了**（只取决于批次大小和窗口），对长上下文场景尤其好。由于信息能顺着层往下传，实际有效上下文比标称窗口更大。([【跳转到 44:05】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2645)、[【跳转到 44:30】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2670))
- **线性注意力（linear attention）**：它**根本不存 KV 缓存**，而是对全部历史信息做某种**压缩表示**。最简单就是把所有 values 加总成一个向量（自然与序列长度无关）；更高级的有 Gated DeltaNet、Mamba 等状态空间模型。([【跳转到 46:10】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2770))

但这里有个绕不开的道理：**"天下没有免费的午餐"——或者这顿午餐其实挺贵的。** 滑动窗口/线性注意力都牺牲了表达能力、会掉一点准确性。常见的折中是**混合架构**：一些层用全注意力、另一些层用局部注意力，交替使用；也可以把全注意力、滑动窗口和线性注意力组合起来，因为它们捕捉的侧重点不同——**想要局部高分辨率信息就用滑动窗口，想要对过往内容的宏观概括就用线性注意力。**([【跳转到 45:20】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2720)、[【跳转到 46:35】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2795))

课堂问答里还有个很精彩的讨论（"大海捞针"问题）：如果上下文极长，而线性注意力必须把整段历史压进很小的表示里，**信息一定会丢失、可能根本检索不到**。所以大家最终还是倾向混合架构——总需要某种长程注意力。Mamba/DeltaNet 这类递归模型也许比滑动窗口更强大（递归时只要看上一个状态，回旋空间更大），但一旦做成固定滑动窗口就"到此为止"了。([【跳转到 47:00】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2820)、[【跳转到 47:51】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2871))

### 8.4 DeepSeek 的压缩/稀疏注意力

讲者特别提到 DeepSeek 还在持续发明新的注意力机制，比如**压缩稀疏注意力（Compressed Sparse Attention，CSA）**、**DeepSeek 稀疏注意力（DSA）** 与**重度压缩注意力（HCA）**。它们的思路可以概括为（[【跳转到 48:45】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2925)、[【跳转到 49:07】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=2947)）：

![DeepSeek 的压缩/稀疏注意力示意：共享 KV 的多查询注意力、滑动窗口 KV、Token 级压缩器把每 m 个 token 压成 1 个、以及 Lightning Indexer 用轻量 query/key 打分挑出要保留的 token 子集。](assets/p10/02947.jpg)

- **压缩**：把每 `M` 个 token 压缩成一个 token（Token-Level Compressor）；
- **稀疏**：不保留全部，而是**挑出一部分子集**——先用轻量的 queries 和 keys 算一次小规模注意力，得到索引分数，据此知道该保留哪些 token（Lightning Indexer），是一种极快、确定该保留哪些 token 的方法。

### 8.5 本节小结

这一节的目标始终是同一个：**减少 KV 缓存，因为 KV 缓存与内存相关，而推理是内存受限的——降内存能直接提升吞吐、降低延迟。** 低维 KV 缓存可以从**跨层、跨 head、跨 head 维度**等各个方向做；也可以用 local attention、linear attention，还有很多其他方法。关键前提是：**在不损害准确性的前提下做到。**

## 九、量化与剪枝：从系统与模型层面把模型变小

前面是从**架构**层面减少 KV 缓存；这一节换两个角度。结论先行：**量化（quantization）从系统层面降低数字精度来省内存，剪枝（pruning）则直接从模型里"剪掉"不重要的部分再修补回来；两者都能在可控的精度损失下提高吞吐、降低延迟。**([【跳转到 50:04】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3004))

### 9.1 量化：降低数字精度

**量化的核心思路是降低数字的精度**：用更少的比特表示每个权重/激活，于是内存占用更小、吞吐更高、延迟更低。选项很多，范围可以从 **bf16 一直到 int4**。显然，代价是要担心准确性。([【跳转到 50:04】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3004)、[【跳转到 50:29】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3029))

![量化的两条路线与进阶方法：训练后量化（PTQ）便宜、逐层/逐张量定 scale 和零点，GPTQ 用 Hessian 信息补偿误差；激活感知量化（AWQ）则发现少数激活通道数值很大，给对应权重保留高精度（fp16→int3，内存降 4 倍、提速 3.2 倍）。](assets/p10/03104.jpg)

### 9.2 QAT vs PTQ，以及 GPTQ 与激活感知量化

- **量化感知训练（Quantization-Aware Training，QAT）**：如果怕量化把模型搞砸，可以**带着量化意识去训练**。做法是在前向传播里**先量化、再反量化**，训练时模拟量化误差，让权重去适应它，量化效果通常更好。代价是**训练成本高昂、规模大**。
- **训练后量化（Post-Training Quantization，PTQ）**：先训练好模型、再做量化，**便宜得多**，是更常见的做法。最直接的做法是逐层或逐张量分别确定缩放因子（scale）和零点（zero point），但效果通常没那么好。
- **GPTQ**：利用**海森矩阵（Hessian）** 信息逐层量化，同时**追踪并修正那些传播到未量化权重里的误差**，效果更好。
- **激活感知量化（Activation-aware Quantization，AWQ）**：核心观察是——**有些激活通道的数值很大，跟这些通道打交道的权重就更重要**。于是给这些权重**多分配精度**：比如整个矩阵保持 int3，只在少数几个重要通道上给 FP16。幻灯片给出的数字很直观：`fp16 → int3` 能带来 **4 倍内存下降、3.2 倍加速**。

([【跳转到 50:54】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3054)、[【跳转到 51:19】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3079)、[【跳转到 51:44】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3104)、[【跳转到 52:09】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3129))

### 9.3 剪枝与蒸馏

**模型剪枝（pruning）** 简单粗暴但有效："拿一个大模型，把其中一部分切掉，然后再修补一下。" 典型流程（以 NVIDIA 的一篇论文为例）是（[【跳转到 52:30】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3150)、[【跳转到 52:51】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3171)、[【跳转到 53:30】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3210)）：

![NVIDIA 的剪枝/蒸馏流程：先评估每个 layer/head/channel 的重要性，排序后剪掉不重要部分，再用喜爱数据做后训练/蒸馏把性能修回来；成功把 15B 压到 8B 而准确率几乎不受影响。](assets/p10/03171.jpg)

1. **评估重要性**：一般会准备一个**校准集**，把输入跑一遍模型，主要看激活值（activations）的大小；
2. **排序并剪掉**：挑出最关键的隐藏单元甚至整层，直接移除；
3. **后训练/蒸馏修复**：此时模型效果还不行，用你关心的数据或任务再训练一下，把性能修回来。

这里有个经验性观察：**某些通道的激活值会远高于其他通道**——激活值高就认为它重要、要保留下来（那些"死单元"数值接近零，可以剪掉）。这个方法之所以有效，正是因为模型**实际就是这么被训练出来的**，你可以利用这个特点。当然也有边界情况：如果一个神经元的值"始终为 100"，直接移除会整体出错，这时得结合偏置（bias）等办法处理。([【跳转到 54:25】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3265)、[【跳转到 55:40】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3340))

剪枝的效果不错：NVIDIA 的工作**成功把一个 15B 的模型压缩到 8B，准确率没怎么受影响，而且整个过程所需的数据量要少得多。** 从更高层面看，这些方法可以归为两条路：要么**设计一种更快的架构从头训练**，要么**用原始模型的权重去初始化一个更快的架构**（架构可能不同，拼出一个"弗兰肯斯坦"式的模型），**再用蒸馏把这个更快的模型修好**。([【跳转到 53:30】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3210)、[【跳转到 53:55】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3235))

## 十、推测解码与动态负载：无损加速和线上服务的系统技巧

前面所有方法（GQA、MLA、量化、剪枝）都是**有损**的——能大幅压缩，但可能牺牲精度。这一节讲三件"更优雅"的事：**无损的推测解码，以及两个应对真实线上动态负载的系统技巧（连续批处理、分页注意力）。** 结论先行：**推测解码利用"检查比生成快"的不对称性，一次接受多个 token 且保持无损；系统技巧则借用操作系统思想来管理 KV 缓存与批次调度。**([【跳转到 56:03】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3363))

### 10.1 推测解码：检查比生成快

**推测解码（speculative decoding，也叫 speculative sampling）** 的核心洞察是一个非常反直觉的不对称性：**检查（评估）一个序列比逐个生成它要快得多。** 回想一下，预填充阶段可以并行地对所有 token 编码、同样给出概率分布，是计算受限、速度很快的；而生成只能逐个进行。所以我们利用这种不对称性（[【跳转到 56:28】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3388)、[【跳转到 56:53】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3413)）：

1. 用一个**便宜的草稿模型（draft model）** 先顺序生成 `K` 个 token（比如 4 个）；
2. 用真正在乎的**目标模型（target model）** **并行地**审查这些 token、算出它们的 logits，决定接受还是拒绝。

两边就此平衡：草稿模型更小更便宜，虽然受内存限制要逐个生成，但问题不大；目标模型虽然又大又贵，但它是**并行处理一批 token**，所以也不会太吃力。

![推测解码算法（Speculative Sampling）：草稿模型 p 自回归采样 K 个 token，目标模型 q 并行算 logits；以 min(1, q/p) 的概率接受，否则从残差分布 (q−p)₊ 采样并退出本轮，保证输出与目标模型精确同分布。](assets/p10/03488.jpg)

**接受/拒绝的数学**（本质是拒绝采样的变体，但**总能从目标模型得到精确样本**，因此是**无损**的）：对每个草稿 token，以概率

```text
accept with probability  min(1, q(x)/p(x))
```

来接受它（这里 `p` 是草稿模型分布、`q` 是目标模型分布）：如果 `q` 比 `p` 大很多，`q` 越大我们就越倾向接受；否则就从**残差分布** `(q - p)₊` 归一化后采样，并退出本轮。([【跳转到 58:33】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3513)、[【跳转到 58:58】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3538))

参数选择有个权衡：**草稿 token 太少**，没怎么利用上目标模型的批处理能力；**太多**，被拒绝的概率就大了。实践中 **3 到 4 个**是比较平衡的点。理想情况下，草稿模型应**尽量贴近目标模型**（用蒸馏来做）；前面讲的各种 KV 缓存压缩手段，其实也可以用来得到一个便宜的草稿模型。([【跳转到 59:23】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3563))

### 10.2 连续批处理与选择性批处理

真实线上服务的负载是**动态**的，不像训练那样整齐：请求到达时间各不相同、共享的前缀也不一样、长度参差不齐，形成"参差的数组（ragged array）"。([【跳转到 59:48】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3588))

**连续批处理（continuous batching）** 由 **ORCA** 系统提出，是一个很早但很关键的做法。它的思路是**迭代级调度（iteration-level scheduling）**：在解码的每一步里，为批次中所有序列各解码一个 token；**某个序列生成结束就立即剔除，新请求一进来就加进批次**，继续处理。所以你的批次是**动态更新**的——旧的完成即踢出、新的随即进入，不必等整个 batch 全部跑完。([【跳转到 60:13】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3613)、[【跳转到 60:38】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3638)、[【跳转到 61:03】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3663))

![连续批处理（Orca）：训练是规整的密集 token 块，而推理是长度参差的数组；做法是逐步解码、完成即移除、新请求随时加入批次，批次动态更新。](assets/p10/03638.jpg)

但这里冒出一个问题：之前批量处理的前提是**所有序列维度一致**，张量里每个切片形状都一样；可现在每个请求长度不同，怎么办？这就引出**选择性批处理（selective batching）**：注意力计算依赖于序列长度，3×3 和 9×9 的运算没法高效共享张量，所以注意力部分要单独处理；但**非注意力的部分（尤其是占了大量 FLOPs 的 MLP 层）可以把所有序列拼接成一个超大序列，一起处理**。([【跳转到 61:25】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3685)、[【跳转到 61:50】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3710))

### 10.3 分页注意力：把操作系统思路搬进来

**分页注意力（PagedAttention）** 是 vLLM 论文提出的核心机制（也是 vLLM 最早、最关键的创新）。它要解决的是**KV 缓存如何存储**的问题——而这会带来**碎片化（fragmentation）**，就像以前硬盘需要"磁盘碎片整理"一样。碎片化主要有两种（[【跳转到 62:03】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3723)、[【跳转到 62:28】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3748)、[【跳转到 62:53】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3773))：

- **内部碎片（internal fragmentation）**：因为不知道生成何时停止，你只能按一个**最大 token 上限**预留缓冲区，于是预留了一大批内存却常常用不上，纯属浪费；
- **外部碎片（external fragmentation）**：不同请求之间留下一些**太小、没法有效利用**的空隙，也成了浪费。

![分页注意力要解决的问题：按最大长度预留导致内部碎片（大量槽位预留未用），请求之间又留下外部碎片；解决办法是借用操作系统思想，把序列的 KV 缓存切成不连续的小块（block）按块对齐、用索引管理。](assets/p10/03783.jpg)

解决方案非常"计算机系统"：既然是搞系统的人、对操作系统很熟，那就照老办法来——**把一个序列的 KV 缓存切成不连续的小块（block）**。块具体放在物理内存哪里不重要，只要**按块对齐、并能通过索引追踪每块的位置**就行。这样一来，**不同请求若共享相同前缀，就可以共用同一块 KV 缓存**（比如把序列切成大小为 4 的小块，"Four score and seven years ago..." 这样的前缀就能被多个请求复用）。([【跳转到 63:03】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3783)、[【跳转到 63:53】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3833))

### 10.4 copy-on-write 与前缀缓存

分页机制带来两个非常实用的收益（[【跳转到 64:09】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3849)、[【跳转到 64:14】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3854)）：

1. **共享 system prompt 的 KV 缓存只算一次**：如果很多用户用的是同一个 system prompt，你就不用为每个请求都重新计算一遍；
2. **同一 prompt 生成多个回复**：很多应用场景里，你用同一个 prompt、却想生成多个不同的回复，这时也可以共享这个 prompt 的 KV 缓存，只让各自独特的回复分头输出。

![copy-on-write 与前缀共享：同一个 prompt 生成多个样本时共享物理 KV 块；若两个样本采到相同 token 就沿用，采到不同 token 就拆块各自续写（引用计数 2→1），从而尽可能复用前缀缓存。](assets/p10/03894.jpg)

实现这个共享的机制叫 **写时复制（copy-on-write）**：保留共享的部分，然后看两个样本——如果它们恰好采样到**相同的 token**就继续沿用同一块；如果采样到了**不同的 token**，就把这个块**拆开、各自往下续写**。本质上，你是在**尽可能多地共享前缀缓存（prefix caching）**。此外 vLLM 还有一系列其他优化，比如 kernel 层面的融合改进，这里就不展开了。核心思路始终是：**借用操作系统里的概念来管理推理。**([【跳转到 64:54】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=3894))

## 小结

1. **推理极其重要、且与训练本质不同**：训练是一次性成本，推理是每天反复支付的账；在 agent 时代，生成的大部分 token 不给人读，算力投入几乎没有上限。
2. **"快"有三个指标**：TTFT（开始生成前的等待）、延迟（单查询出词速度）、吞吐量（多查询总速度）。它们适用于不同场景，且**延迟与吞吐量常常相互制约**（小 batch 延迟低、大 batch 吞吐高）。
3. **概念框架**：用 einops 式记号描述张量，用**算术强度**判断计算/内存受限——H100 的算术强度约 **295**，而推理生成阶段注意力只有约 **1**。
4. **核心结论**：**预填充是计算受限、生成是内存受限**。MLP 本质是一次大矩阵乘法（强度约 `B×T`，batch 大就不怕）；注意力生成阶段强度仅 `S/(S+1)≈1`，且**不随 `B` 缩放**——这就是推理的根本瓶颈。
5. **缩小 KV 缓存**是主要优化方向：GQA（head 间共享，缩到 `K/N`）、MLA（压缩成潜变量 `C`，DeepSeek V2 压到 512+64）、跨层注意力（layer 间共享）、滑动窗口/局部注意力（与序列长度无关）、线性注意力（不存 KV、压缩历史）、DeepSeek 的压缩/稀疏注意力。它们都有"天下没有免费的午餐"的代价，常用混合架构平衡。
6. **量化与剪枝**从系统/模型层面把模型变小：QAT（模拟量化误差、训练贵）vs PTQ（便宜）、GPTQ（用 Hessian 补偿）、AWQ（给重要激活通道留高精度，fp16→int3 省 4 倍内存、提速 3.2 倍）；剪枝则移除不重要部分再后训练/蒸馏修复（15B→8B）。
7. **推测解码是无损加速**：草稿模型先出 K 个 token，目标模型并行校验，以 `min(1, q/p)` 接受、否则从残差 `(q−p)₊` 采样；K 太小浪费批处理、太大易被拒，实践中 3~4 个较平衡。
8. **动态负载要用系统思想**：连续批处理（Orca，完成即剔除、新请求随时加入）、选择性批处理（MLP 拼成大序列共享）、分页注意力（把 KV 切成块、解决内部/外部碎片）、copy-on-write 与前缀缓存（共享 system prompt 和同一 prompt 的多个回复）。
9. **所有方法遵循同一原则**：**减少 KV 缓存占用，同时尽量不损害精度**；此外可引入系统领域的分页与推测执行思想。
10. **开放的未来方向**：Transformer 的注意力/KV 结构天生对推理不友好，而状态空间模型、线性注意力、扩散模型等"为推理而生"的新架构仍有巨大改进潜力。下一讲回到缩放定律的第二部分。([【跳转到 66:58】](https://www.bilibili.com/video/BV11LEA6eEuj/?p=10&t=4018))

## 关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 推理（inference） | 用训练好的模型根据 prompt 生成回复；反复发生、成本持续 |
| TTFT（首 token 时间） | 从发出查询到第一个 token 出现前的等待；基本等于 prefill 时间 |
| 延迟（latency） | 单个用户一次查询里 token 冒出来的速度（秒/token） |
| 吞吐量（throughput） | 面向多查询时每秒能处理多少 token（token/秒） |
| 算术强度（arithmetic intensity） | FLOPs 除以传输字节数，即每搬一个字节做了多少计算，越大越好 |
| H100 的算术强度 | `989e12 / 3.35e12 ≈ 295`，用于判断运算是否计算受限 |
| 计算受限 / 内存受限 | 运算强度大于硬件强度则计算受限（好），否则内存受限（差） |
| einops 记号 | 用字母表示维度、用颜色区分收缩/常规/批处理维度 |
| 收缩维度（红色） | 同时出现在两个操作数、并从结果中消失的维度 |
| 批处理维度（蓝色） | 同时出现在两个操作数并保留在结果中的维度 |
| 预填充（prefill） | 输入完整 prompt、并行编码并填满 KV 缓存（T = S） |
| 生成（generation） | 逐个按序生成新 token、复用已有 KV 缓存（T = 1） |
| KV 缓存（KV cache） | 为每个序列/每 token/每层/每 head 缓存键和值向量 |
| 分组查询注意力（GQA） | 查询头数不变，KV 减少到 K 组；KV 缓存缩到 K/N |
| 多头潜在注意力（MLA） | 把激活压缩成潜变量 C，只缓存 C，需要时再还原 K/V |
| 跨层注意力（cross-layer） | 在 layer 之间共享 KV：只算部分层，其余复用上一层 |
| 滑动窗口注意力 | 每个 token 只看最近 K 个 token，KV 缓存与序列长度无关 |
| 线性注意力 | 不存 KV、把全部历史压成固定大小的表示；与序列长度无关 |
| 量化（quantization） | 降低数字精度（bf16→int4）来省内存、提吞吐、降延迟 |
| QAT / PTQ | 量化感知训练（前向里模拟量化、训练贵）／训练后量化（便宜） |
| GPTQ | 用 Hessian 信息逐层量化并补偿误差的训练后量化方法 |
| 激活感知量化（AWQ） | 给数值大的激活通道对应权重保留高精度，其余低精度 |
| 剪枝（pruning） | 移除不重要的隐藏单元/层，再后训练/蒸馏把性能修回来 |
| 推测解码（speculative decoding） | 草稿模型先出 K 个 token、目标模型并行校验，无损加速 |
| 连续批处理（continuous batching） | 逐步解码、完成即剔除、新请求随时加入的动态批次调度 |
| 选择性批处理 | 注意力分别处理，非注意力（MLP）把序列拼成一个大序列共享 |
| 分页注意力（PagedAttention） | 把 KV 缓存切成不连续小块、按块索引，消除内部/外部碎片 |
| 写时复制（copy-on-write） | 共享前缀块；采样到不同 token 时才拆块各自续写 |
| 前缀缓存（prefix caching） | 重复使用相同前缀（如 system prompt）已算好的 KV 缓存 |
